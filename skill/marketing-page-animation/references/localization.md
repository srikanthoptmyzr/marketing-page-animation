# Localization

Used in phase 13, and while writing copy in earlier phases. Goal: the generated page is localized by the website's own mechanism, exactly like every other page, and every visible string, including text inside reconstructed product UI, is real, editable, translatable content.

## The one question

Before anything else, answer: **"How does the existing Optmyzr website handle localization?"** Then follow that system.

Do not ask "how should I build localization?" This skill never creates a parallel i18n system, a client-side translation layer, a new file format or a new language switcher for the shipped page. The only exception is when no existing mechanism can be found at all, and then the skill stops and asks (see "If no mechanism can be found").

## Confirmed mechanism (was: working assumptions — all now verified)

Every point below was checked against the repo on 2026-09-29 and held true. Full detail with sources in `site-kit/localization.md`.

- Hugo renders a **separate static page per language**, with its own content files. English is served at the **root with no prefix** (`defaultContentLanguageInSubdir = false`); the others sit under `/es/`, `/de/`, `/fr/`, `/jp/`. Good for SEO: every language is crawlable, has its own metadata, and works without JavaScript.
- Source language is English. Active languages are **es, de, fr, jp**; Danish (`da`) is disabled via `disableLanguages`. The Japanese key is **`jp`**, not `ja`.
- English content lives under `content/english/...`, other languages under their own `content/<lang>/...`. Structured data under `data/<lang>/...`. UI strings in `i18n/<lang>.toml`, used as `{{ i18n "key" }}`.
- Only fields named in the translatable-key list are translated. A separate skip list is left alone — and a skip-key **halts recursion**, so nothing nested under it is translated either. URL fields receive language prefixes.
- A translation step (in Marketing-OS, the localization agent) mirrors changed English files into each active language with per-language tone and brand-name rules, and a translation parity validator checks the result.

Consequences that hold whatever the details turn out to be:

- **The shipped page has no client-side language files and no language switcher of its own.** It uses the site's switcher, in the site's header, through the kit.
- **English source only** goes into the handoff bundle. The dev team's localization process produces the other languages.

## Step 2. Integrate with the mechanism

1. **Write English source in the site's format.** Page copy and scene content as block fields in the page's front matter (or wherever the discovery says). Small UI labels as keys in the English UI string file. Structured lists in the English data folder. Use the file locations from the discovery, or from `hugo-bookshop-target.md` marked unverified.
2. **Use existing field names.** Read the translatable-key list first. Name scene fields from that list wherever a matching name exists (headings, descriptions, button text, list items and similar). A field name outside the list is silently left untranslated, so:
   - Do not put translatable text in a skip-listed field, and do not put non-text values (ids, images, dates) where they would be translated.
   - If a scene truly needs a new translatable field name, that is a **dev-team configuration change**. Flag it in the handoff. Do not edit the configuration.
   - If the list is not available, mark every new field name `unverified`.
3. **Reuse the site's chrome.** Header, footer, navigation and language switcher come from the kit. Do not rebuild them or change how they localize.
4. **Follow the URL and link rules.** Internal links are ordinary site-relative links so the process can prefix them per language. Use the site's helper for language-aware links if one exists.
5. **Follow the metadata rules.** Fill title, description and any social fields the way sibling pages do, in English, so they are translated with the page. Do not hand-write `hreflang` or canonical tags if the layout generates them.
6. **Do not translate yourself in a repo.** In Mode B, if a translation process exists, do not write other-language files. Hand over English source, run or request the process, and run the parity validator. Write translations directly only if the user asks and the discovery shows that is the site's normal practice.
7. **Preserve shortcodes and template expressions exactly.**

### Preview-only language toggle (Mode A)

So reviewers can see the layout in other languages before handoff, the preview page may include a clearly labelled, preview-only language toggle using Claude-drafted translations. It is a review aid, not a localization system:

- It is never part of the handoff bundle and never mirrors the site's real switcher behavior.
- Drafted translations are labelled "preview only, not reviewed" and are not included in the bundle.
- It reads the same field structure as the English source, so nothing about the page's data model is invented for it.
- Include it only when the kit lists more than one active language.

**Drive the site's own language picker — do not add a second control.** The header already has
one, and a reviewer should be exercising the real thing. A separate widget teaches them a
control that will not exist on the published page.

The captured picker's `selectLanguage()` dispatches a **`language-changed`** event carrying
`{code, label}`, and only navigates when a translation URL exists — which it does not for a
local preview, so the switcher is already inert there and safe to hook. Listen for the event,
swap the text, and no-op `window.showLangFallbackToast` (the site shows a "no translation"
toast that would be wrong here, since the translation is on screen). Alpine keeps the picker's
own label and selected state in step for free.

**Implementation that works** (from the Explorer build):

- Tag every swappable string in the markup with `data-i18n="<key>"`. Do not guess at selectors.
- **Do not put a disclosure in the chrome.** The real header has no "preview only" note, and the
  preview must behave exactly like the site — a reviewer checking layout should see the page a
  visitor would see. Put the disclosure where it belongs: `reports/validation.md`, the preview
  README, and a `console.info` for anyone inspecting the page.
- **Localize the product UI inside the scenes too.** Rule 9 makes scene text content, so a
  reconstructed table's column headers, entity list, status pills and toolbar labels switch
  language with the page. Tag them under a namespace (`data-i18n="sc.<key>"`) so the swap can
  tell chrome from page copy. Account names, ids and figures are **data**: they stay put. A
  scene that stays in English while the page turns German is the giveaway that the product UI
  was treated as a picture rather than as content.
- **Tag everything, or the page looks half-translated.** A partial pass is worse than none: a
  German heading over English body copy, or a Japanese page with an English table inside it,
  reads as broken. Work from a list of every visible string — headings *and* body paragraphs,
  benefit bullets, the trust strip, CTA, FAQ questions **and** answers, case-study copy, and the
  UI text in **every** scene. After building, diff the tagged keys against the translation file
  and fail on any gap; then switch language in the browser and count how many tagged nodes still
  hold their English text. The only ones that should is a short list you can name: acronyms
  (ROAS), product names (Google Ads) and the vendor's own brand.
- **Strip the hooks from the bundle.** `data-i18n` is preview scaffolding. In the repo the same
  text comes from Hugo fields, so shipping the attribute implies a client-side mechanism that
  does not exist and misleads whoever integrates the page.
- Keep the drafted copy in its own module (`i18n_preview.py`), imported by the build and
  written **only** into `preview/`. Assert it is absent from `handoff/` before you ship.
- Read the English text out of the DOM on load and keep it as the baseline, so switching back
  to English restores the source rather than a re-translation.
- Set `document.documentElement.lang` on switch (`jp` maps to `ja`), so screen readers and
  font fallback follow.
- Label the control in the control itself: *"Preview only — drafted, not reviewed. The shipped
  page uses the site's own per-language pages."* A reviewer must never mistake it for the real
  switcher.
- **The preview inlines its scripts in `<head>`**, so the toggle must wait for
  `DOMContentLoaded`. Wired at parse time it finds no control and silently does nothing — it
  looks like "localization is broken" when the page is in fact working as designed.

Languages come from the kit, not from the page: en, es, de, fr, jp. Danish is disabled and
must not appear.

## If no mechanism can be found

Only if the discovery finds no localization mechanism at all (for example the target site is not the one this skill was built for):

1. Stop and tell the user plainly.
2. Ask the dev team what the intended approach is.
3. In the meantime, keep all text in fields and string files (never hard-coded), produce English only, and list the gap in the handoff.

Never design a full i18n architecture unprompted.

## Localize the entire page

Every visible string is data handled by the mechanism above. This includes:

- Navigation, header, footer and language-related labels (from the kit)
- Headlines, body copy, feature descriptions, supporting content
- CTAs, buttons, labels, form text
- Product UI scenes: menus, dashboard labels, table headers, buttons, tooltips, notifications, messages, AI or system responses, placeholders, empty states
- Alt text, ARIA labels and scene descriptions
- Metadata: title, description, social text

If a string is visible, spoken by a screen reader, or read by a search engine, it must be a field or a string key. Nothing is baked into an image, SVG or script.

## Rules for localizing reconstructed product UI

The scene is real UI, not a picture of UI.

1. **Live text.** All scene text is real DOM text rendered from fields or string keys. No text in images, SVG paths, canvas or CSS `content` (except decorative glyphs).
2. **Editable in the CMS.** Scene text should be editable by the team like any other block content, through the fields the component exposes.
3. **The spec marks each string** `translate: true` or `false`:

   | Kind of text | Translate? |
   |---|---|
   | Product chrome: menus, buttons, column headers, placeholders, tooltips | Yes |
   | Demo content that illustrates the feature: conversation, AI responses, notifications, recommendations | Yes, if the page should read naturally in each language. Decide once per page and apply consistently |
   | Product and brand names, feature names | No, follow the site's brand-name rule |
   | Synthetic names, emails and IDs from the privacy pass | No. The same safe values in every language |
   | Numbers, dates, currency | Format for the locale, do not translate |

4. **Fidelity is structural.** Localization changes the words, not the layout, hierarchy, sequence or interaction shown in the reference. The reference is English (or another single language); the scene keeps its structure in every language.
5. **Same keys, one structure.** All languages fill the same fields in the same scene structure. No language-specific markup branches.
6. **Privacy carries over.** Translated demo content uses the same synthetic values. Translators must not receive originals, and the privacy leak scan runs over each language's files (Mode B) or the English bundle (Mode A).
7. **Locale formatting.** Numbers, dates, currency and units follow the locale via the site's helper where one exists. Animated counters format their final value the way the page's language does.
8. **Accessibility text.** Scene descriptions, `aria-label`s and alt text are fields too, and are translated.

## Text expansion and responsive behavior

The translation system decides which text loads. The components must survive any length. Do not assume English dimensions.

- **Expansion.** German and French often run 30 to 40 percent longer than English, and some short English words become long compounds. Design and test for at least +40 percent, and for very short text too.
- **No fixed text boxes.** No fixed widths or heights on any element containing text, in scenes or in the page around them. Use `min-`/`max-` sizes, `flex`/`grid` with `minmax`, and let containers grow. Prefer `min-height` over `height`, and `padding` over fixed size for buttons and chips.
- **Wrapping.** Labels, buttons and chips wrap or grow instead of overflowing. Use `overflow-wrap: anywhere` or `hyphens: auto` where needed with the right `lang`. Never clip text with hidden overflow unless truncation is deliberate and has a full-text fallback.
- **Truncation.** Ellipsis only where the reference truncates (for example a table cell). Provide the full value in a tooltip or accessible name.
- **Priority elements.**
  - *Headlines*: wrap to more lines, keep line height, no fixed line counts.
  - *CTAs*: buttons grow horizontally, then wrap to two lines; on narrow screens become full width.
  - *Navigation*: comes from the kit; check it in the longest language and report breakage as a kit issue rather than patching it.
  - *Cards*: equal-height rows via grid, content-driven heights.
  - *Tables*: allow column widths to flex; let header cells wrap; allow horizontal scroll inside the table container as a last resort on mobile, never on the page.
  - *Product UI messages*: message bubbles and rows size to content, and the scene's vertical space is allowed to grow. Compact variants shorten the *number* of items, not the language.
- **Mobile.** Re-check every compact scene variant in the longest language, since compact variants leave less room. If the longest language does not fit, simplify the structure (fewer items, stacked layout) rather than shrinking text below the legibility limit in `responsive.md`.
- **CJK.** Japanese needs more line height, different line breaking (`line-break`, `word-break: auto-phrase` where supported) and no letter-spacing assumptions. Check fonts cover the script and set fallbacks.
- **Right-to-left.** Only if the config activates a right-to-left language. If so, use logical properties (`margin-inline`, `padding-inline`, `inset-inline`) and mirror only what the reference would mirror. Do not build for it otherwise.
- **`lang` attribute.** Rely on the page's `lang` from the site's layout. Do not hard-code language in scene markup.

## Animation considerations

- **Read rendered text.** Because each language's text is rendered into the page, the scene player reads text from the DOM at run time. Timelines refer to elements, not strings, and hold no translatable text.
- **Duration from length.** Typing and streaming durations are computed from the rendered text length (within the limits in `animation-system.md`), so any language animates at a natural pace. A cap keeps very long text from dragging on.
- **Segmenting.** Split typed or streamed text by grapheme (`Intl.Segmenter`) or by word segmentation for languages without spaces, never by fixed character counts or by spaces alone, so Japanese, accents and emoji do not break mid-character.
- **Reveal by content.** Stagger and reveal steps target elements, so the number of lines a headline wraps to does not matter. Do not animate per line unless lines are measured at run time.
- **Layout stability.** Reserve the final size before text appears (author in the final state, animate opacity and transform only), so longer text never shifts the layout during the animation.
- **Counters.** Format with the locale's separators and reserve width for the widest form.
- **Reduced motion.** Localized text shows in its final state immediately. Nothing depends on a language.
- **Timing budget.** Longer languages get more reading time. Steps that wait for a reader (a message that must be read before the next appears) scale their hold time by text length within a cap.

## Handoff notes for localization

The handoff README must state:

- The English source files and where each belongs.
- The scene's field names, and which of them are not on the site's translatable list (needing a dev-team change).
- Which localization facts were unverified when the page was built, and what to check.
- Which strings are demo content, and the decision on whether to translate them.
- Any draft translations used only in the preview (not included).
- Which languages and viewports were checked for expansion, and any known tight spots.
